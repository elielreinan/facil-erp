ATIVIDADES SEGURAS PARA OUTRA IA
FACIL ERP + GFACILERP
================================

OBJETIVO
--------
Este documento lista atividades que podem ser executadas sem:

- acessar Supabase ou qualquer banco de dados;
- usar dados reais de clientes, fornecedores ou funcionários;
- receber .env.local, tokens, senhas ou chaves;
- usar service_role, sb_secret ou JWT secret;
- criar, alterar ou excluir registros reais.

As tarefas devem ser feitas localmente, preferencialmente com dados fictícios
criados somente em memória ou em mocks de teste. Antes de começar cada tarefa,
faça uma cópia local ou crie um commit separado.

COMO ENVIAR PARA OUTRA IA
-------------------------
Envie somente:

- o nome da atividade;
- a pasta do projeto: FacilERP ou GFacilERP;
- o código-fonte necessário;
- o erro completo, se houver;
- o resultado do build ou teste local.

Nunca envie:

- qualquer arquivo .env ou .env.local;
- URLs privadas, tokens, senhas ou chaves;
- exportações do banco;
- nomes, e-mails, documentos ou dados de funcionários;
- capturas de tela que contenham informações internas.

REGRAS PARA TODAS AS ATIVIDADES
--------------------------------
- Não conectar ao Supabase.
- Não alterar schema.sql nem executar SQL.
- Não criar tabelas, usuários ou buckets.
- Não instalar dependências sem autorização.
- Não executar npm audit fix --force.
- Não remover autenticação, RLS ou validações existentes.
- Não substituir consultas reais por dados fictícios no código de produção.
- Usar mocks apenas em testes isolados.
- Executar o build após mudanças de código.
- Informar arquivos alterados e comandos executados.

ATIVIDADE 1 - REVISAR INTERFACE E RESPONSIVIDADE
------------------------------------------------
Objetivo:
Garantir que as telas funcionem em janela pequena, média e grande.

Prompt:
"No projeto [FacilERP ou GFacilERP], revise a interface sem acessar banco,
Supabase ou arquivos de ambiente. Verifique sidebar, cabeçalho, tabelas,
formulários, modais e mensagens em larguras de 320px, 768px e 1280px.
Corrija somente problemas de layout, overflow, espaçamento e responsividade.
Não altere regras de autenticação nem invente dados. Rode o build ao final e
liste os arquivos modificados."

Sucesso:
- Nenhuma tabela ou formulário causa overflow horizontal inesperado.
- Botões e campos permanecem utilizáveis em tela pequena.
- O build termina sem erro.

ATIVIDADE 2 - ACESSIBILIDADE
----------------------------
Objetivo:
Melhorar a utilização por teclado e leitores de tela.

Prompt:
"Faça uma revisão de acessibilidade no projeto [nome]. Não use banco nem
credenciais. Corrija labels associados aos campos, foco de modais, navegação
por teclado, aria-labels de botões somente com ícone, contraste e mensagens
de erro. Preserve o visual atual e não altere o rodapé. Rode o build e
descreva os testes manuais realizados."

Sucesso:
- Campos possuem labels compreensíveis.
- Elementos interativos funcionam com teclado.
- Modais recebem e devolvem foco corretamente.
- Erros são identificáveis sem depender somente de cor.

ATIVIDADE 3 - ESTADOS DE CARREGAMENTO E ERRO
---------------------------------------------
Objetivo:
Padronizar loading, vazio e erro sem alterar a origem dos dados.

Prompt:
"Revise as telas do projeto [nome] e padronize estados de carregamento,
lista vazia, erro e tentativa novamente. Não conecte ao banco, não crie
fallback com dados fictícios e não esconda erros. Use componentes e padrões
já existentes. Se testes precisarem de dados, use mocks somente nos testes.
Rode o build ao final."

Sucesso:
- Usuário entende quando a tela está carregando.
- Lista vazia não é confundida com erro.
- Falha de consulta apresenta mensagem clara e opção de tentar novamente.

ATIVIDADE 4 - TESTES DE COMPONENTES COM MOCKS
---------------------------------------------
Objetivo:
Criar testes locais para componentes sem chamadas de rede.

Prompt:
"Adicione testes unitários ou de componentes para [arquivo ou tela].
Mocke somente as dependências externas e use dados fictícios mínimos dentro
do teste. Não chame Supabase, não use .env, não use dados reais e não altere
o código para facilitar artificialmente o teste. Cubra renderização, campos
obrigatórios, cancelamento, confirmação e exibição de erro. Informe se o
projeto já possui runner de testes antes de instalar qualquer pacote."

Sucesso:
- Os testes são determinísticos.
- Nenhum teste depende de internet, Supabase ou credencial.
- Cenários de sucesso e erro são cobertos.

ATIVIDADE 5 - VALIDAÇÃO DE FORMULÁRIOS NO CLIENTE
------------------------------------------------
Objetivo:
Melhorar mensagens de validação antes do envio.

Prompt:
"Revise a validação visual do formulário [nome] sem acessar banco ou API.
Garanta campos obrigatórios, formatos, limites de tamanho, números inválidos
e mensagens acessíveis. A validação do cliente não deve ser apresentada como
substituta da validação do servidor. Não altere schema, policies ou consultas.
Adicione testes locais com entradas fictícias e rode o build."

Sucesso:
- Entradas inválidas recebem mensagem específica.
- O usuário consegue corrigir o campo sem perder os demais valores.
- Nenhuma validação depende de dados externos.

ATIVIDADE 6 - ORGANIZAÇÃO E DOCUMENTAÇÃO DO CÓDIGO
--------------------------------------------------
Objetivo:
Facilitar futuras atualizações sem mudar o comportamento.

Prompt:
"Revise a organização do código do projeto [nome] sem alterar comportamento,
autenticação ou acesso a dados. Remova duplicação segura, extraia componentes
visuais repetidos e atualize README ou documentação técnica com os comandos
locais de instalação, build e execução. Não documente nem copie segredos.
Preserve os padrões existentes e rode o build."

Sucesso:
- Componentes repetidos ficam reutilizáveis.
- README explica como instalar, executar e compilar localmente.
- Nenhum segredo aparece na documentação.

ATIVIDADE 7 - PADRONIZAR CONFIRMAÇÕES E NOTIFICAÇÕES
----------------------------------------------------
Objetivo:
Melhorar a experiência antes de ações destrutivas.

Prompt:
"Revise confirmações e notificações da interface sem acessar banco. Toda
ação destrutiva deve pedir confirmação imediatamente antes de ser executada.
Mensagens devem informar sucesso ou erro sem afirmar que algo foi salvo
quando a persistência falhou. Não altere a chamada ao Supabase; apenas ajuste
interface, estados e mensagens. Rode o build."

Sucesso:
- Exclusões possuem confirmação.
- Cancelar não altera dados ou estado indevidamente.
- Mensagens não apresentam sucesso falso.

ATIVIDADE 8 - PREPARAR CONTRATO DE INTEGRAÇÃO COM MOCK
-----------------------------------------------------
Objetivo:
Documentar uma futura integração sem criar conexão real.

Prompt:
"Crie uma especificação local e fictícia para integração entre FacilERP e
GFacilERP, sem implementar chamadas de rede e sem usar bancos. Documente
versionamento, formato de requisição e resposta, erros, idempotência e
permissões em termos genéricos. Use exemplos claramente fictícios, sem
nomes, e-mails, tokens ou IDs reais. Não publique segredos e não altere
policies. Se criar código, use apenas um adaptador mock isolado e rode o build."

Sucesso:
- O contrato possui versão e exemplos fictícios.
- A documentação deixa claro que não é um endpoint ativo.
- Nenhuma credencial ou dado pessoal aparece.

ATIVIDADE 9 - REVISAR CONFIGURAÇÃO DO APLICATIVO WINDOWS
--------------------------------------------------------
Objetivo:
Identificar problemas de configuração sem gerar instalador nem acessar dados.

Prompt:
"Revise os arquivos de configuração do Tauri e do Next.js no FacilERP.
Não use banco, credenciais ou dados reais. Verifique scripts, caminhos,
output estático, ícones referenciados, permissões declaradas e documentação.
Não altere configurações de produção sem explicar. Faça somente correções
seguras e rode o build web; se cargo não estiver instalado, apenas registre
essa limitação."

Sucesso:
- Scripts e caminhos documentados estão consistentes.
- Nenhuma chave é incluída na configuração do aplicativo.
- O build web passa.

ATIVIDADE 10 - CHECKLIST DE SEGURANÇA SEM CREDENCIAIS
------------------------------------------------------
Objetivo:
Encontrar exposição acidental no código versionado.

Prompt:
"Faça uma revisão estática no projeto [nome] sem acessar internet, banco ou
arquivos de ambiente. Procure chaves, tokens, senhas, service_role, sb_secret,
JWT secret e dados pessoais hardcoded. Não abra nem copie o conteúdo de
.env.local. Verifique também se arquivos sensíveis estão no .gitignore.
Reporte apenas caminhos e tipos de risco, sem reproduzir nenhum segredo.
Não altere arquivos automaticamente sem minha confirmação."

Sucesso:
- Nenhum segredo é exibido no relatório.
- Arquivos de ambiente estão ignorados.
- Falsos positivos são identificados como documentação ou exemplo.

ATIVIDADE 11 - EXECUTAR BUILD E CHECAGENS LOCAIS
------------------------------------------------
Objetivo:
Confirmar que o código atual continua compilando.

Prompt para FacilERP:
"No diretório FacilERP, execute npm.cmd run build. Não inicie servidor,
não acesse Supabase e não altere arquivos. Se falhar, leia o erro e corrija
somente problemas de compilação diretamente relacionados. Ao final informe
o comando e o resultado."

Prompt para GFacilERP:
"No diretório GFacilERP, execute npm.cmd run build. Não inicie servidor,
não acesse Supabase e não altere arquivos. Se falhar, leia o erro e corrija
somente problemas de compilação diretamente relacionados. Ao final informe
o comando e o resultado."

Sucesso:
- O build termina com código 0.
- Nenhum arquivo .env ou segredo foi usado ou exposto.

1. Executar o build local.
2. Revisar responsividade.
3. Corrigir acessibilidade.
4. Padronizar loading, vazio e erro.
5. Melhorar validações de formulários.
6. Adicionar testes com mocks.
7. Revisar confirmações e notificações.
8. Atualizar documentação.
9. Revisar configuração do Windows.
10. Preparar contrato de integração fictício.
11. Fazer revisão estática de segurança.
