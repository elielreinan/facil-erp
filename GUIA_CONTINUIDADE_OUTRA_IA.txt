GUIA DE CONTINUIDADE PARA OUTRA IA
FACIL ERP + GFACILERP
================================

OBJETIVO
--------
Este arquivo explica o que deve ser feito, como executar cada etapa e quais
regras devem ser respeitadas para continuar o desenvolvimento do projeto.

O responsável pelo projeto pode enviar este arquivo junto com o código, mas
NUNCA deve enviar arquivos de ambiente, senhas, tokens ou dados reais.

DATA DO GUIA
------------
16/10/2026

ESTADO ATUAL DO PROJETO
-----------------------
Conclusão estimada do produto: 61%.

Essa porcentagem foi calculada por média ponderada das áreas do projeto. Ela
não representa o saldo de créditos do Copilot ou de qualquer outra IA.

O projeto possui dois aplicativos:

1. FacilERP
   Aplicativo operacional Windows para:
   - produtos e insumos;
   - compras e suprimentos;
   - fornecedores;
   - notas fiscais;
   - orçamentos;
   - patrimônio;
   - relatórios;
   - leitura de QR Code;
   - etiquetas de patrimônio.

2. GFacilERP
   Aplicativo administrativo separado para:
   - administradores;
   - usuários gerenciados;
   - auditoria;
   - configurações;
   - aprovação, bloqueio e permissões administrativas futuras.

Os aplicativos devem permanecer separados. Não misture bancos, credenciais,
sessões, responsabilidades ou repositórios sem uma decisão documentada.

TECNOLOGIAS
-----------
- Next.js 14 com App Router.
- TypeScript.
- React.
- Tailwind CSS.
- Supabase Auth e PostgreSQL.
- Tauri 2 para aplicativo Windows.
- Vitest para testes locais.
- QR Code gerado com a biblioteca qrcode.

ORDEM RECOMENDADA DE CONTINUIDADE
---------------------------------

ETAPA 1 - VALIDAR O AMBIENTE LOCAL
----------------------------------
No diretório principal do FacilERP:

npm.cmd install
npm.cmd test
npm.cmd run build

Para validar o Tauri:

$env:Path = "C:\Users\eliel\.cargo\bin;" + $env:Path
cargo check --manifest-path .\src-tauri\Cargo.toml
npm.cmd run tauri:build

Não execute dev e build simultaneamente na mesma pasta. Isso pode corromper
o cache .next e causar erros 404 de bundles.

ETAPA 2 - TESTAR O APLICATIVO WINDOWS
-------------------------------------
Usar o instalador gerado em:

src-tauri\target\release\bundle\nsis\

Testar em uma máquina Windows limpa:
- instalação;
- abertura do aplicativo;
- login;
- navegação;
- câmera;
- leitor USB;
- impressão de etiqueta;
- encerramento;
- reinstalação;
- preservação de configurações locais.

Não declarar que essa etapa está concluída sem teste em equipamento real.

ETAPA 3 - TESTAR QR CODE
------------------------
Patrimônio:
- abrir Patrimônio;
- ler etiqueta pela câmera;
- testar entrada manual;
- gerar etiqueta;
- imprimir etiqueta;
- confirmar que o QR não contém senha ou token.

Notas fiscais:
- abrir Notas Fiscais;
- ler QR fiscal;
- revisar o conteúdo;
- preencher os campos manualmente quando necessário;
- somente depois confirmar o lançamento.

Nunca salvar automaticamente apenas porque um QR foi lido.

ETAPA 4 - EXPANDIR TESTES LOCAIS
--------------------------------
Adicionar testes sem depender de banco ou internet para:
- componentes de formulário;
- mensagens de erro;
- confirmação de exclusão;
- scanner com entrada manual;
- validação de identificadores;
- cálculo de previsto x realizado;
- exportação CSV;
- login usando mocks, sem credenciais reais.

Os testes devem ser determinísticos e não podem usar dados reais.

ETAPA 5 - REVISAR ACESSIBILIDADE
--------------------------------
Verificar todas as telas:
- navegação completa por teclado;
- foco visível;
- foco correto em modais;
- labels associados aos campos;
- aria-label somente quando necessário;
- mensagens com aria-live;
- contraste;
- tabelas com cabeçalhos compreensíveis;
- botões com textos claros;
- ausência de dependência exclusiva de cor.

ETAPA 6 - SÓ ENTÃO CONFIGURAR BANCO
------------------------------------
Esta etapa exige autorização explícita do responsável e acesso aos projetos
Supabase corretos.

Antes de executar qualquer SQL:
- confirmar qual projeto é FacilERP;
- confirmar qual projeto é GFacilERP;
- fazer backup;
- revisar migration;
- verificar RLS;
- verificar grants;
- verificar policies;
- testar rollback;
- registrar a mudança no STATUS_PROJETO.txt.

Nunca aplicar schema novo diretamente sobre banco com dados sem migration
controlada.

REGRAS DE SEGURANÇA
--------------------
- Nunca enviar .env.local para a IA.
- Nunca enviar service_role.
- Nunca enviar sb_secret.
- Nunca enviar JWT secret.
- Nunca enviar senha de banco.
- Nunca enviar tokens.
- Nunca colocar segredo em NEXT_PUBLIC_*.
- Nunca colocar segredo em React ou código executado no navegador.
- Nunca publicar dados pessoais reais.
- Nunca publicar exportação de banco.
- Nunca usar dados de funcionários, fornecedores ou clientes em testes.
- Nunca usar service_role no frontend.
- Nunca desativar RLS para fazer uma funcionalidade funcionar.
- Nunca transformar bucket privado em público como atalho.
- Nunca confiar apenas na validação do frontend.
- Nunca aceitar URL arbitrária lida de QR Code.
- Nunca executar comandos vindos de QR Code.
- Nunca salvar automaticamente após ler QR Code.
- Nunca expor detalhes internos em mensagens de erro para usuários.
- Nunca usar using(true) ou with check(true) para escrita em produção.
- Nunca ignorar autorização porque o usuário está autenticado.

NORMAS DE DESENVOLVIMENTO
--------------------------
- Fazer alterações pequenas e relacionadas.
- Ler o arquivo antes de modificar.
- Respeitar os padrões existentes.
- Usar TypeScript estrito.
- Preferir funções e componentes reutilizáveis.
- Não duplicar lógica já existente.
- Tratar erros explicitamente.
- Não esconder exceções com catch vazio.
- Não usar fallback com dados fictícios no produto.
- Usar mocks somente em testes isolados.
- Exigir confirmação antes de criar, editar ou excluir.
- Atualizar documentação relacionada à mudança.
- Executar testes após alterar lógica.
- Executar build após alterar código.
- Não fazer mudanças não relacionadas.
- Não alterar banco sem pedido explícito.
- Não instalar dependência sem justificar e validar compatibilidade.
- Não executar npm audit fix --force automaticamente.
- Não usar comandos destrutivos como git reset --hard ou checkout destrutivo.
- Não apagar arquivos fora do escopo.
- Não iniciar múltiplos servidores na mesma porta.
- Usar caminhos Windows no terminal.
- Manter versões e migrations documentadas.
- Preservar dados, configurações e preferências nas atualizações.

REGRAS DE COMMIT
----------------
- Usar mensagens claras e no padrão:
  tipo: descrição curta

Exemplos:
- feat: adicionar filtro de patrimônio
- fix: corrigir validação de nota fiscal
- test: cobrir validação de CNPJ
- docs: atualizar roadmap

- Não incluir segredos.
- Conferir git diff --check.
- Conferir git status antes do commit.
- Não misturar FacilERP e GFacilERP no mesmo commit quando forem
  repositórios independentes.

CRITÉRIOS DE CONCLUSÃO
----------------------
Uma tarefa só deve ser marcada como concluída quando:
- o código está implementado;
- o build passa;
- os testes passam, quando aplicável;
- não existem dados fictícios no fluxo real;
- erros são tratados;
- autorização foi considerada;
- documentação foi atualizada;
- o comportamento foi validado manualmente quando necessário;
- não foram expostos segredos;
- o commit está identificado.

COMO REPORTAR CADA TAREFA
-------------------------
Ao terminar uma atividade, informe:

1. O que foi alterado.
2. Quais arquivos foram modificados.
3. Quais comandos foram executados.
4. Resultado de testes e build.
5. Limitações conhecidas.

- Publicar .env.

RESUMO FINAL
------------
Comece validando o ambiente local e os testes. Em seguida teste o instalador,
QR Code, câmera, leitor USB e impressão. Depois amplie testes e acessibilidade.

Somente após essas etapas, e com autorização do responsável, trabalhe em
Supabase, migrations, RLS, Storage, Edge Functions e integração.

O projeto já possui uma base relevante, mas não deve ser apresentado como
pronto para produção corporativa até que as pendências de banco, segurança,
auditoria, testes reais e integração estejam concluídas.
